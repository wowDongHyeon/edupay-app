## 1. 한 줄 결론

**병목·실패 지점은 단 하나, callQuvi(QUVI = SQL 생성 서비스)다.** 동시 요청이 몰리면 QUVI가 ~37초 매달리다 `null`을 반환하고 워크플로우가 그 자리에서 status=FAILED. **동시 10명 지속만으로 성공률이 44%까지 붕괴**한다. baseline(순차)은 100% 성공이므로 실패는 순전히 동시성 유발. 병목은 DB가 아니다.

> 대조: 앞선 대량 데이터(1000만 건) 테스트는 인덱스로 해결됐다 = **DB는 스케일한다. 스케일 안 되는 건 QUVI SQL 생성 서비스.**

> ★ 최종 확정본은 §8(2차 실측). §2~7은 1차(계단식) 관측이며 §8이 이를 정정한다.

## 2. 실측 수치

### 2.1 baseline (동시 1, 순차 20회)
- 성공률 **100%** (20/20)
- workflow_duration: med **2.52s** / p95 **3.22s** / max 6.95s
- session 생성: ~8ms (무시 수준)

- SSE keep-alive 지연 문제 없음(한 건 ~2.5s, 타임아웃까지 안 감)

### 2.2 계단식 부하 (10 → 50 → 100 → 200)
- **50 VU 구간에서 성공률 84%로 하락 → 90% 임계 abort(56초 지점).** 100·200은 도달 못 함.
- 완료 25건 중 성공 21 / 실패 4(err_flaky = result success=false)
- workflow_duration(완료분): med 6.24s / p95 7.55s (baseline p95 3.22s의 2.3배 → PASS 기준 ② 초과)
- **http_req_duration p99 49.7s / max 49.8s** — 지연 꼬리 폭발
- **주의**: 이 84%는 낙관치. abort로 25건만 집계, 나머지 50 interrupted는 서버가 계속 돌려 상당수 FAILED로 떨어짐(§3).

## 3. 어드민 트레이스 교차검증 — 핵심 발견

부하 요청 367건이 어드민 `답변 분석`에 기록됨. 소요시간이 **두 덩어리**로 갈림:

| 유형 | 스텝수 | 소요 | 토큰(In) | 실제 상태 |
|---|---|---|---|---|
| 완주 성공 | 10 스텝 | 18.5s | 11,609 | COMPLETED (SQL 생성+답변 O) |
| **실패** | 4 스텝 | 8.1s | 2,908 | **status: FAILED** (SQL 생성 전 사망) |

### 3.1 "빠른 8.1초"는 성공이 아니라 실패였다
4스텝 요청의 NL2SQL 노드 NODE STATE:
```json
{ "intentType": "DOMAIN_QUERY", "status": "FAILED", "currentStep": 0, "totalSteps": 2 }
```
- 질의를 `DOMAIN_QUERY`(SQL 필요)로 **분류는 정확히** 했으나, NL2SQL 노드에서 **FAILED** → callQuvi(SQL 생성) 진입 전 사망.
- 그래서 4스텝에서 잘리고 토큰도 앞 2단계(COORDINATOR 1,668 + PLANNER 1,240 = 2,908)만 찍힘.
- 최신 페이지 10건 중 **7건이 이 FAILED 시그니처** → 체감 실패율 ~70%(동시 구간).

### 3.2 완주 성공(18.5초) 단계별 내역 = callQuvi가 병목
| # | 단계 | 유형 | 시간 | In | Out |
|---|---|---|---|---|---|
| 1 | COORDINATOR | LLM | 2.4s | 1,668 | 4 |
| 2 | PLANNER | LLM | ~0 | — | — |
| 3 | classify | LLM | 3.2s | 493 | 105 |
| 4 | NL2SQL | NODE | ~0 | | |
| 5 | date_filter | LLM | 2.7s | 2,437 | 30 |
| 6 | **callQuvi** | QUVI | **8.9s** | **5,906** | 117 |
| 7 | executeSQL | JS | ~0 | | |
| 8 | column_label | LLM | 0.6s | 432 | 10 |
| 9 | respondent | LLM | 0.6s | 673 | 22 |
| 10 | NL2SQL_RESPONDENT | NODE | ~0 | | |

- **callQuvi(SQL 생성) = 전체의 절반**: 8.9초 + 입력 5,906토큰(전체 입력의 절반).
- 전체 18.5초 = 6번의 LLM 호출을 **순차로 합산**(병렬 없음). 동시 요청이 같은 내부 Qwen LLM에 몰리면 매 단계가 다 느려지고, callQuvi에서 완주 실패(FAILED)로 떨어짐.
- callQuvi 입력이 큰 이유: SQL 생성 단계라 스키마 + 유사도 검색으로 끌어온 Semantic expression 예시를 프롬프트에 다 싣기 때문.
- **10 스텝** = reporter_plan OFF가 이미 반영된 상태(옆 프로젝트 작업과 일치).

## 4. 근본 원인

동시 요청 → 내부 Qwen LLM 인퍼런스 포화 → 요청당 6번의 순차 LLM 호출(특히 입력 5,906토큰의 callQuvi)이 밀림 → 일부는 지연(18s), 상당수는 NL2SQL 노드에서 **FAILED**. DB/인덱스와 무관. **LLM 인퍼런스 처리량이 동시 용량의 천장.**

## 5. 동시 용량을 높이는 지렛대 (효과 순)

1. **callQuvi 입력 토큰(5,906) 감량** — 가장 큰 효과. Semantic expression을 LEAN하게(top-K 예시·스키마 컨텍스트 축소). CLAUDE.md 기존 원칙과 정확히 일치. 프롬프트 축소 = 단계 시간 단축 + 동시성 여유 확보.
2. **토큰 변동(완주 시에도 11.6k) 원인 규명** — 유사도 검색이 끌어오는 컨텍스트량을 상한/결정화.
3. **LLM 인퍼런스 측 확장** — Qwen 인스턴스 병렬/배치, 큐잉·타임아웃·재시도 정책 점검(FAILED를 재시도로 흡수).
4. 파이프라인 추가 슬림화(column_label·respondent OFF 등)는 각 0.6s로 효과 작음 — 우선순위 낮음.

## 8. ★ 2차 실측 (단일 고정 동시성) — 근본원인 확정

계단식(§2.2)은 abort로 초반 저부하 성공이 표본을 지배해 낙관 편향이 있었다. 그래서 **고정 동시성 1레벨을 지속**하는 방식으로 재실측(`STAGE=single`, abort OFF로 전체 표본 확보).

### 8.1 동시 10명 지속 30초 결과
- **성공률 44%** (8/18) — 나머지 56% FAILED. interrupted 0(온전한 표본) → 계단식 88%보다 신뢰도 높음.
- err_flaky = 10 (전부 result success=false) → **k6가 서버 FAILED를 정확히 집계**(성공판정 신뢰 확인).
- 성공 요청: **~4.2초, ~13,000토큰**(빠르고 완주). 실패 요청: **~39.6초, ~6,840토큰**(매달리다 사망).
- **핵심 정정**: 1차에선 "토큰 많으면 느림"으로 보였으나, 2차에선 성공이 오히려 토큰 더 많고 빠름 → **토큰 양은 원인이 아니다.**
- 실패가 전부 **39.5~39.6초에 밀집** = 고정 타임아웃(~37~40초) 신호.

### 8.2 callQuvi null — 사망 지점 확정
39.6초 FAILED 트레이스(wf 1a04d9cc) 단계별:

| # | 단계 | 유형 | 시간 | In | Out |
|---|---|---|---|---|---|
| 1 | COORDINATOR | LLM | 4.1s | 1,668 | 4 |
| 2 | PLANNER | LLM | 8.6s | 1,240 | 56 |
| 3 | classify | LLM | 1.0s | 499 | 110 |
| 4 | NL2SQL | NODE | ~0 | | |
| 5 | date_filter | LLM | 8.4s | 2,437 | 30 |
| 6 | **callQuvi** | QUVI | **37.3s** | 792 | 17 |
| 7 | executeSQL | JS | — | | (SQL 없음) |

- **callQuvi Input**: "이번 달 결제 몇 건이야 [조회 날짜범위: 20260701~20260728]" (정상)
- **callQuvi Model Output: `null`** ← QUVI가 37.3초 만에 null 반환
- 전체 39.6초 중 **37.3초가 callQuvi 한 단계**. 나머지 LLM 단계도 부하로 늘었지만(PLANNER 8.6s·date_filter 8.4s), **실제 사망은 callQuvi**.

### 8.3 확정 근본원인
**callQuvi(QUVI SQL 생성 서비스)가 동시 처리를 못 버틴다.** 지속 부하에서 QUVI가 슬롯을 못 잡은 요청은 ~37초 대기 후 `null` → 워크플로우 FAILED. 성공 = QUVI 즉시 응답(4.2s 완주). 전형적 **서비스 동시성/풀 고갈 + 고정 타임아웃** 패턴. 병목이 "LLM 파이프라인 전반"이 아니라 **QUVI 단일 서비스**로 좁혀짐.

### 8.4 ★ 3차 실측 (정밀 계단식 2→4→6→8→10) — 8.1~8.3을 뒤집음

각 레벨을 순차(비겹침)로 30s씩 돌리고 레벨별 분리 집계.

| 동시 | 성공률 | p95 지연 |
|---|---|---|
| 2 | 92.9% (13/14) | 3.29s |
| 4 | 96.7% (29/30) | 3.71s |
| 6 | 91.2% (31/34) | 4.20s |
| 8 | 93.2% (41/44) | 5.08s |
| 10 | **95.6% (43/45)** | 12.24s |

- **성공률은 동시 2~10에서 안 무너진다** — 전부 91~96% 평평. **§8.1의 single-10 = 44%가 재현 안 됨**(같은 동시 10인데 95.6%).
- 무너지는 건 **지연**: p95 3.3s(2) → 12.2s(10), 약 4배. 대부분 실패가 아니라 "느린 성공".
- 실패 10건이 전 레벨에 흩어짐(2에도 1건) = **동시성과 무관한 배경 실패율 ~5~8%** = operia 원래 flakiness.

### 8.5 ★ 변동의 원인 = 공용 LLM 경쟁 (동현 확인)

- **내부 LLM(Qwen)을 사내 여러 부서가 공동 사용.** callQuvi의 "슬롯"은 우리 전용이 아니라 회사 전체 공유 자원.
- 그래서 same 동시10인데 44%(8.1) ↔ 95.6%(8.4)로 출렁인 것 = **우리 동시성만이 변수가 아니라, 그 순간 다른 부서의 공용 LLM 부하가 섞임.**
- 해석 3분할:
  - **95%+ (best)** = 공용 LLM이 놀 때 = 우리 파이프라인 순수 처리 상한.
  - **44% (worst)** = 공용 LLM 경쟁 심할 때 겪는 바닥.
  - **변동 폭 자체** = 우리 성능이 외부 부서 부하에 노출된 리스크.
- **운영 함의**: 우리 코드를 최적화해도 공용 LLM이 붐비면 실패. → **전용 슬롯/쿼터 확보**가 callQuvi 슬롯 확장만큼 중요.

### 8.6 미해결 단서 (다음)

- **더 높은 레벨(15·20·30)** — 1차 계단식은 50에서 붕괴. 진짜 절벽은 10~50 사이일 것.
- **단일 유저(teststu05) 동시 = per-user 제한 가능성**은 아직 미배제(공용 LLM 경쟁으로 상당 부분 설명되나, 유저 풀로 교차확인 권장).

[오페리아 학습] AI채팅 동시접속 부하 테스트 결과

■ 목적
여러 사용자가 동시에 AI채팅에 질문할 때 오페리아(NL2SQL AI)가 몇 명까지 견디는지 검증.
개발서버(10.0.2.5) nginx 게이트웨이로 직접 요청, teststu05 기준 측정.

■ 테스트 조건
- 도구: k6 (동시 사용자 수를 자동으로 늘려가며 측정)
- 동시 접속: 2명 → 50명까지 단계별로 증가 (각 단계 30초)
- 대표 질의: "이번 달 결제 몇 건이야" (고정)
- 성공 기준: 답변이 정상 완료된 요청 (SQL 생성 실패 = 실패로 집계)

■ 핵심 결과 (한 줄)
오페리아는 사용자가 몰려도 요청을 "실패"시키기보다 "느려지는" 방식으로 버틴다.
=> 한가한 시간대 기준, 동시 50명까지도 성공률 99% 이상. 다만 사람이 몰릴수록 응답이 느려짐.

■ 동시 접속 수별 응답 시간
 동시 10명 →  약 6초   (쾌적)
 동시 20명 → 약 11초   (허용)
 동시 30명 → 약 21초   (느림)
 동시 50명 → 약 50초   (사실상 사용 불가, 타임아웃 문턱)

=> 처리 능력의 천장 = 초당 약 2건.
=> 응답 10초 이내를 "쾌적"의 기준으로 보면, 실질 동시 접속 상한은 약 20명.
   그 이상은 실패는 안 나도 응답이 20~50초로 느려져 쓰기 어려움.

■ 왜 이런가 (병목)
- 각 질문은 여러 단계(질문 분석 → SQL 생성 → DB 조회 → 답변)를 순서대로 거침.
- 이 중 SQL 생성 단계(callQuvi)가 가장 무겁고, 여기가 동시 처리의 천장을 결정.
- 사용자가 몰리면 이 단계에서 줄을 서게 되어 전체 응답이 느려짐.
  (주방이 1초에 2접시만 만들 수 있어, 손님이 많으면 요리 속도는 그대로고 대기줄만 길어지는 것과 같음)

■ 중요 변수 — 사내 공용 LLM 경쟁
- 오페리아가 쓰는 LLM(Qwen)은 사내 여러 부서가 공동으로 사용.
- 같은 동시 10명이라도 다른 부서가 LLM을 많이 쓰던 순간에는 성공률이 크게 떨어짐(측정 중 44%까지 하락한 사례).
- 즉 실서비스 안정성은 우리 동시 접속 수보다 "그 순간 공용 LLM의 혼잡도"에 더 크게 좌우됨.

■ 결론 및 개선 방향
1. 현재 구조에서 쾌적 사용 기준 동시 접속 상한은 약 20명(처리량 초당 2건).
2. 더 늘리려면:
   - (근본) 공용 LLM에서 오페리아 전용 슬롯/쿼터 확보 → 다른 부서 경쟁 영향 차단
   - (보조) SQL 생성 단계 프롬프트 경량화(Expression Top K 축소) → 요청당 처리 속도↑
3. 실패한 요청은 재시도할 필요 없음(사용자에겐 실패 안내로 충분). 재시도는 오히려 혼잡을 키움.
   => 해결은 "재시도"가 아니라 "처리 용량 확보"가 맞음.

※ 상세 수치·트레이스: edupay-app/loadtest/ 결과 문서 참조.
